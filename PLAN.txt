PART 3: PXE ROM SUPPORT IN 6502.ts
----------------------------------


Goal: the preview emulator's main backend (6502.ts, `tools/stellerator`) runs PXE ROMs, so they no longer fall back to gopher2600.

### What a PXE ROM is

PXE stands for Phantom logic's eXtended Elf kernel (ZackAttack's thread on AtariAge,
https://forums.atariage.com/topic/381582-pxe-pronounced-pixie-new-elf-based-bb-kernel/ : it is part of batari Basic v1.9, has demo
programs such as `full-playfield.bas`, `paddle-scrolls-pf.bas` and `quadtari-demo.bas`, and runs in gopher2600 and Stella). From that
thread: it is a new kernel written in C and compiled to an ELF file for the cartridge's ARM chip (the Chameleon Cart's is a 64 MHz
Cortex-M3), mostly compatible with DPC+ programs, with up to 60 KB of ROM and no bank switching commands in the program: the ARM
driver does the bank switching itself by watching the 6507's jumps and returns. It adds per-line playfield and background colors,
horizontal scrolling, a 40 pixel playfield and more than 50 extra variables.

- A PXE ROM is an ELF file, run by an ARM program that drives the 2600's bus itself (the "ELF" cartridge type, in the same family as
  the Harmony/Melody and CDF boards, but with no fixed 6502 program: the ARM code executes the 6507 cycles through a bus library).
- In this repo the pieces are `public/bb19/includes/PXE-pre.arm` (the start of the ELF), a 6502 ROM image that begins with the text
  `PXE-ROM`, and `PXE-post.arm` (the rest of the ELF). The kernel (`PXE_kernel.asm`) hands the ARM code the addresses it needs
  (`drawscreen`, `BKCOLS`, `PFCOLS`, `C_function`, the player variables, ...). `PXEheader.asm` and `PXEfooter.asm` build the ROM.
- The app does not build PXE ROMs itself yet; gopher2600 loads one from memory (changelog 0.52.7). The reference implementation is
  gopher2600's ELF cartridge: `tools/gopher2600-wasm/vendor/github.com/jetsetilly/gopher2600/hardware/memory/cartridge/elf/` (about
  3,900 lines of Go: `elf.go`, `memory.go`, `strongarm*.go`, `gpio.go`, `stream.go`, `pxe.go`).

### What 6502.ts has and lacks

- Has: cartridge classes for DPC+ and CDF (`CartridgeDPCPlus.js`, `CartridgeCDF.js`, about 300 lines each), and a `harmony/Soc.js` (196 lines)
  that wraps `thumbulator.ts` (David Welch's Thumb emulator compiled to JavaScript) with a RAM and flash bus.
- Lacks: an ELF loader, any ELF cartridge, the bus-library ("strongarm") functions, and a way for ARM code to run the 6507's cycles.
- The ARM code in this repo's PXE ELF (`PXE-pre.arm` + a 64 KB ROM blob + `PXE-post.arm` makes a valid ELF; `readelf -A` on it) is
  **ARMv6S-M, Thumb-1 only** (`Tag_CPU_arch: v6S-M`, `Tag_THUMB_ISA_use: Thumb-1`), even though the first Chameleon boards have a Cortex-M3.
  So `thumbulator.ts` is a good base: no Thumb-2 core is needed, only the few ARMv6-M instructions it may lack (`BL`, `MSR`/`MRS`,
  `DMB`/`DSB`/`ISB`, to be checked against the ELF's `.text` and `.RamFunc`). The ELF has `.text` (7 KB), `.RamFunc` (8.7 KB of code
  that runs from RAM, the timing-critical part), `.rodata` (67 KB of the kernel's tables), `.bss` (11 KB) and a `.bbpxe` section.

### Steps

0. **Recon (1 day; the ISA question is already answered, see above).** Get real PXE ROMs (the examples under `C:\tmp\pxe-examples` and any `.elf` the user has). Read the ELF with
   `arm-none-eabi-readelf -h -S -s -A` (toolchain in `C:\tmp\armtc`): the CPU architecture tag, sections, symbols (`pRAM`, the bus
   functions it imports), and the relocations used. Decide Thumb-1 or Thumb-2. Run each ROM in gopher2600 and record screenshots
   and a few frames of TIA writes as the reference to compare against.
1. **ELF container (2 days).** Parse ELF32 little-endian in TypeScript: sections, symbols, relocations (the ARM REL types gopher2600
   handles in `memory.go`), the `PXE-ROM` 6502 blob, and the PXE section. Build the memory map (flash/ROM, RAM, the PXE palette region
   `0x700-0x7ff`, pRAM). Unit-test against the same files with golden section dumps.
2. **ARM core (2 to 4 days).** Wire `thumbulator.ts` to the ELF memory map (flash, RAM, `.RamFunc` in RAM) and run the kernel's functions
   one at a time against gopher2600 (same inputs, compare registers and memory). Add whichever ARMv6-M instructions it lacks. The cycle
   counts need to be good enough for the bus timing in step 3.
3. **Bus library ("strongarm") (4 days).** Port the functions in `strongarm_definitions.go`, `strongarm_vcslib.go`,
   `strongarm_support*.go` (`vcsLibInit`, `vcsInitBusStuffing`, `vcsJmp3`, `vcsWrite3`, `vcsLda2`, ...) as functions the emulator
   catches when the ARM code branches to them, and that run the 6507 bus cycles (bus stuffing: the ARM puts opcodes and data on the
   data bus while the 6507 runs). This is the part that has to match the 6502.ts CPU's cycle-exact mode, so expect the most debugging here.
4. **Cartridge class and detection (1 day).** `CartridgeELF` in the style of `CartridgeCDF`, `CartridgeFactory`/`CartridgeDetector` picking
   it from the ELF magic number, 6502.ts's `Soc` hooks for GPIO and streams (`gpio.go`, `stream.go`).
5. **PXE specifics (2 days).** `pxe.go`: pRAM, palette origin and memtop, the per-scanline palette writes, and how they reach the
   TIA color output. 6502.ts needs a way to take a palette color from cartridge memory per line.
6. **App integration (1 day).** `tools/stellerator/worker-entry.js`: accept ELF ROM bytes, remove the automatic fallback for PXE once
   it is solid, keep the gopher2600 fallback while it is not. Update the emulator settings text and the wiki.
7. **Verification (2 days).** Compare frame by frame with gopher2600 on every sample ROM (pixel diff of the first few hundred frames),
   check input, audio and the debug overlay. Add the samples and a small Node test that loads each ROM headless.

Total: about 2 to 3 weeks of work, most of it the bus library and its timing.

### Recon results (2026-11-01, step 0 done on a real ROM)

A PXE ROM can be built here and now: `C:/tmp/pxe/build.mjs` (Node, uses the WASI .wasm files of public/bb19 through node:wasi: preprocess, 2600basic,
postprocess, dasm, the same chain as src/hooks/bb-compiler.js) compiles a program that starts with `set kernel PXE`. A 4 line program and an 8 row
playfield program (C:/tmp/pxe/t1.bas, t2.bas) both give a 91,670 byte main.bin with 61,000 bytes of ROM left. (The AtariAge example attachment
`C:/tmp/pxe-examples/full-playfield.bas` is a Cloudflare error page, not a program.) So the toolchain side already works; the app only lacks a way to
pick the PXE kernel (nothing in src mentions it) and the emulator side below.

What the ROM is, from `arm-none-eabi-readelf`/`objdump` on that main.bin (the ELF is `C:/tmp/pxe/out1/main.bin`):
- ELF32 little endian, type REL (a relocatable object: nothing is linked, the cartridge loader places the sections and applies the relocations),
  ARMv6S-M, Thumb-1 only (every instruction is plain Thumb-1: ldr, movs, adds, lsls, blx, bl, push/pop, uxtb/uxth/sxtb/sxth, muls, ...; no
  msr/mrs/dmb, no Thumb-2).
- Sections: .text 7.4 KB, .RamFunc 8.8 KB (code that runs from RAM), .text.startup 96 B, .rodata 67 KB (holds `DpcpBin`, a 65,536 byte 6502 ROM image,
  and tables such as `PaddleOverblankBin`, 115 bytes), .init_array (one entry, the C++ constructor of `pRAM`), .bbpxe 4 B (`pRAM`, the pointer gopher2600
  reads to find the PXE memory), .bss 11 KB.
- Relocations are few and simple: 415 R_ARM_ABS32, 30 R_ARM_THM_CALL, 1 R_ARM_TARGET1. No MOVW/MOVT, no PC22, no veneers.
- The program is C++: a `CPU` class (execute, read, write, ADC, SBC, ...: 8.9 KB object `cpu`) is a software 6502 that runs the game's 6502 code (`DpcpBin`)
  inside the ARM, a `MultiSprite` class (the kernel, object `kernel`, 2.3 KB) draws the screen, `elf_main` is the entry point.
- It imports only 18 symbols: the bus library functions vcsLda2, vcsLdx2, vcsLdy2, vcsSta3, vcsStx3, vcsSty3, vcsStx4, vcsJmp3, vcsNop2, vcsNop2n, vcsWrite5,
  vcsRead4, vcsStartOverblank, vcsEndOverblank, plus memcpy, memset, randint, ReverseByte. They are called through pointers (`blx` through a literal pool
  word with an R_ARM_ABS32 relocation), never through BL.

What that means for 6502.ts (this changes the plan above):
1. The 6507 does not run a program that is in the ROM. The ARM program runs the game in its software 6502 and tells the real 6507, one instruction at a time,
   what to do: vcsLda2(x) means "the 6507 executes LDA #x" (bytes $A9, x), vcsSta3(zp) "STA zp" (bytes $85, zp), vcsJmp3 a JMP back to $1000, vcsNop2 a NOP,
   vcsRead4(addr) an LDA absolute that returns the byte read, vcsWrite5(zp, data) LDA # then STA. (gopher2600 injects these bytes on the data bus when the 6507
   fetches; the ARM sits in the cartridge.) vcsWrite3 is the bus stuffing one: the cartridge drives the data bus during the write cycle of an STA/STX/STY/SAX so
   the TIA sees `data` whatever the registers hold; vcsStartOverblank/vcsEndOverblank copy a small overblank routine into the console's RAM and hand the 6507 to it.
2. Because every ARM to 6507 interaction is "execute this instruction", 6502.ts does not need the strongarm timing machinery. The cartridge object can be a
   coroutine: when the 6507 fetches a byte from cartridge space and the queue of bytes is empty, run the ARM (thumbulator.ts) until it calls the next vcs function;
   the function (an import trapped by `trapOnBx32`, like CDF's calls, if the imports get even (ARM state) stub addresses) queues its bytes and stops the run
   (return a nonzero trap code), and the next byte request resumes it (write r15 and call `run` again, without `reset`). The 6507 is the real 6502.ts CPU, so the
   cycle counts come out right by themselves. The speed of the ARM is not modelled.
3. Needed: (a) an ELF REL loader and linker (the three relocation types above, section placement: flash for .text/.rodata, RAM for .RamFunc/.bss/.data, the
   .init_array run before elf_main), small; (b) the 18 imports in JS (memcpy, memset, randint, ReverseByte are trivial), vcsRead4 returning the byte the 6507
   actually read, and the bus stuffing write (a hook on the CPU's write for the next write, or a cartridge-side bus override); (c) `Soc`-like memory map for the
   thumbulator (it exists in harmony/Soc.js; its RAM and flash sizes are 8 KB and 32 KB, so a version with 64 KB+ flash and about 24 KB of RAM is needed; thumbulator.ts
   takes any bus object); (d) a cartridge class that the worker picks by the ELF magic. thumbulator.ts (0.3.1, MIT) has the hooks needed: `run(cycles)`,
   `trapOnBx32`, `trapOnInstructionFetch`, `readRegister`/`writeRegister`, `stopAddress`.
4. "PXE specifics" (step 5) shrinks: gopher2600's pxe.go only records, for the debugger, which palette address a color came from (`LastPXEPalette`); the colors reach the
   screen through ordinary TIA writes, so no palette hook is needed in 6502.ts. (To confirm by reading the frames once the first ROM runs.)
5. The estimate drops: no strongarm bus-timing port. Rough: ELF loader 1 to 2 days, Soc and imports 2 days, coroutine and bus stuffing 2 to 3 days, debugging against
   gopher2600 frames 2 to 3 days.

How it works (the design of the research above held; two details were different):
- The cartridge keeps no ROM: the 6507 reads the address space at offsets from $1000. A bus library call puts the bytes of its instruction at `next` (offset) and moves `next`: vcsNop2n(n)
  puts one NOP and skips n-1 addresses (the 6507 reads what the data bus still holds, the NOP); vcsJmp3 puts 4C 00 10 and sets `next` back to 0 (the bytes are dropped once the 6507 has read the
  jump); vcsStartOverblank puts JMP $0080 and the 6507 runs the routine the program wrote in RAM; vcsEndOverblank sets the byte at the last address of the cartridge to 0, which that routine
  is waiting for (LDX $FFFF, BNE). The ARM program is resumed only when the 6507 reads the offset where the next instruction goes (the dummy read of an implied instruction counts: it reads the
  next opcode), or reads the last address while in the overblank routine. vcsRead4 returns the A register of the CPU when the program is resumed.
- `ReverseByte` is a data table (256 bytes), not a function: elf.js gives imported tables an address after the sections.
- thumbulator.ts: `run()` returns 2 at a BLX to an even address; r15 reads as the address of the instruction + 4 and the instruction run on resume is the one 2 below r15, so a resume writes
  r14 = return address | 1 and r15 = return address | 1 + 2. thumbulator aborts (throws) on an instruction it does not know; none came up in these ROMs.

### CDF, CDFJ and CDFJ+ as a starting point

6502.ts already runs CDF, CDFJ and CDFJ+ (`CartridgeCDF.js`, versions 0, 1 and 2). They are a poor place to start for PXE: in those boards the
6507 runs the cartridge's own 6502 code and the ARM only fills data streams on request, so none of the bus-driving machinery PXE needs is
there. What they do give: the `Soc` class around `thumbulator.ts`, the pattern for a cartridge with ARM RAM and flash, and test ROMs
that already pass, which is a way to check any change to the ARM wiring does not break them. Start from the ELF cartridge (step 1) and reuse
that part of CDF.
